# VFX Refinery

Create original, readable combat VFX for this project's **1980s anime mecha, toon shading, deep shadows, Grand Chase combat readability and Armored Core machinery**. This style is a primary acceptance criterion, not a final color pass. Avoid primitive early-anime looks, fantasy spell language, goofy motion, chibi/cartoon puffs and rainbow glitter. Ice becomes cryogenic machinery; poison becomes radiation or industrial contamination.

## Always apply

- Use this skill for every project VFX task and revision. Read [art-direction.md](references/art-direction.md) and the relevant entries in `Docs/VfxIterationNotes.md` before designing. The accepted initial baseline and iteration summary are recorded there. On feedback, reassess the skill as well as the effect.
- Design visibly distinct layers, not merely multiple child systems: different source masks, depth, size, color/value, opacity, motion and onset. Preserve negative space and grayscale density from opaque interiors to transparent edges. Check perceptual silhouette diversity; extra systems, rotations and source filenames can still repeat the same recognizable stamp. Avoid straight decorative lines and stretched line accents; use broken, curved or irregular shapes. Apply the feedback-specific motion and reference guidance in [art-direction.md](references/art-direction.md).
- Consider context-appropriate real light casting, HDR bloom/glow, localized heat distortion, source preparation and visible material aftermath. These are supported authoring options, not mandatory on every VFX. Use the installed URP Volume framework and the `urp-postprocessing` skill for scene support; distinguish bloom from receiver illumination. See [particle-authoring.md](references/particle-authoring.md).
- Use **Unity Particle System** for most work. Prefer installed/native materials and modules. When their capability is insufficient, document the concrete gap and use a small **ShaderLab/HLSL** shader. Shader Graph is a fallback; VFX Graph requires a demonstrated GPU/simulation need, not merely an available vendor graph. The old `unity-vfx-graph` skill is supplemental only.
- Build finished effects from scratch under `Assets/_Project/VFX/<EffectName>/`. New effect-specific scripts, ScriptableObject profiles, materials, shaders, prefabs, meshes, textures and animation live there. Create only needed folders. Existing shared gameplay systems remain in their established responsibility folders; do not migrate old effects incidentally.
- Treat supplied package trees as reference libraries. `Reference` means study only; **never ship, instantiate in gameplay, nest, derive a variant from, or lightly recolor a finished vendor effect**. `VFXSource` means a reusable building block, conditional on compatibility and style review. Read [source-library.md](references/source-library.md) to search the catalog and inspect dependencies. A source label is not approval of its appearance or production readiness.
- Author scenes, prefabs, materials, importers and labels with Unity APIs through the official `unity mcp` / Pipeline workflow. Discover live commands first; see `Docs/UnityMcpSetup.md` and the `unity-cli` skill. Preserve unrelated dirty assets and restore editor/play state after previews. Never hand-edit Unity YAML.
- ScriptableObjects own tuning and setup; components hold references and instance state. Never mutate shared profiles/material assets in gameplay. Use per-renderer property blocks only where supported, otherwise owned material instances with cleanup. Native Particle System/Animator/physics/Cinemachine remain responsible for their domains.
- No automated tests unless explicitly requested. Validate with static review, compilation, isolated manual runtime inspection and actual rendered output. Do not create extra clients or builds for ordinary local VFX work.

## Work from brief to observed result

1. **Inspect the request and integration.** Establish the effect's gameplay event, source, target, scale, camera view, world/combat plane, timing, environment and lifetime. Read current callers, damage/authority boundaries and renderer settings. Infer routine details from the project; ask only for material missing direction. Do useful independent work while awaiting answers.
2. **Write a compact effect breakdown.** State the physical/mechanical interpretation, silhouette, palette, phases and per-phase purpose. For a layered explosion distinguish flash, core, directional ejecta, pressure, debris, smoke and residual heat as needed. Use a layer table with onset, lifetime, source asset, orientation, space, material and cost. Not every effect needs every layer, collision, bounce or light.
3. **Consult evidence.** Search `Docs/VfxSourceCatalog.csv` for suitable source assets and a few relevant final references. Inspect their hierarchy/modules/material dependencies read-only using `AgentScripts/Inspect-VfxReference.cs` (or Unity APIs). Learn timing, streams and composition; reconstruct a different project effect. Read only the relevant package-guide notes in [source-library.md](references/source-library.md).
4. **Author the smallest useful solution.** Read [particle-authoring.md](references/particle-authoring.md) for phased systems, contact direction, collision, bounce, lighting, shaders, lifecycle and authority. Prefer an authored prefab with native child Particle Systems over rebuilding every module in runtime code. Extend the existing emitter only for the job it already serves. Give special projectile, projectile-hit and projectile-reaction interactions their own focused VFX scripts when needed; do not put travel, damage, reaction, light and cleanup in one universal controller.
5. **Integrate explicit event context.** Pass source and receiving target plus snapshots/contact data. Calculate direction from actual incoming velocity or source-to-target geometry, apply it to the VFX root and directional modules, and align contact-facing layers to the surface normal. Never use a constant facing/right vector for all hits. Separate target penetration, surface rebound and residual smoke frames. Cosmetic collisions cannot apply damage.
6. **Validate once, then return for user review.** Read [review-and-learning.md](references/review-and-learning.md). Make one coherent revision against the brief/feedback, compile, and perform a brief gameplay-scale preview of onset, main action and decay when useful. Verify frame/time progression before claiming runtime validation. Check only interactions changed by this revision; retain earlier evidence for unchanged behavior. Correct concrete technical failures, such as a missing phase, broken shader, wrong attachment or truncated lifetime. Do not run repeated capture/tuning cycles to choose artistic preferences for the user. A successful API call or one bright screenshot is not visual acceptance.
7. **Record and deliver.** Maintain `Docs/VfxEffectOrigins.csv` when producing effects, using one row per reused source and studied reference, including archive container, GUID/path, derived path, role, changes and evidence. Follow the schema in [source-library.md](references/source-library.md). Keep a concise per-effect breakdown/validation note next to its authored files. Update native Unity asset labels through MechaAssetLabels; do not maintain a per-file classification inventory. Record demonstrated feedback learning and narrowly improve this skill. Report what changed, validation performed and any unobserved behavior; do not claim user approval.

## Stop conditions and scope

Default to one coherent implementation pass and a short technical/visual sanity check, then deliver the reviewable result and wait for user feedback. User-led iteration is the artistic acceptance loop. Further self-iteration is justified by a concrete technical defect or an explicit request, not by a desire to polish indefinitely. If an input/tool blocks meaningful work, preserve the result and identify the specific limitation. Do not silently accept a known bad result, invent evidence, repeatedly import packages, or change global time/network settings to make a demo look better. Author context-appropriate rendering support when needed for the requested VFX; the user explicitly authorized scene post-processing, bloom/glow and supporting effects in feedback revision 5. Keep changes scoped, editable and documented rather than globally replacing the game look.

This skill is a workflow, not a preinstalled replacement VFX runtime. Add interaction code only while implementing a concrete effect. The initial package scan and skill installation do not themselves demonstrate a new effect's visual quality.
