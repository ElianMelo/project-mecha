User decisions recorded 2026-10-14; apply these to future features.

1. Use this order: Unity built-in systems/components, official Unity packages, established widely used maintained packages, and custom solutions only as a last resort. Inspect installed capabilities first, check project compatibility, and record the missing capability before introducing a custom replacement. Combat VFX use Particle Systems; cameras use Cinemachine; animation uses Animator; room walls use colliders. Custom scripts connect these systems rather than reimplementing them.
2. ScriptableObjects own authored configuration: movement, input timing, attack/skill definitions, presentation clips, enemy behavior, camera/room bounds, toon lighting and particle profiles. Components reference configuration and retain per-instance state. Runtime code does not write back to configuration assets.
3. Keep PlayerInputs, PlayerMovement and PlayerAttack separate. Animation and effects have separate presentation components. Keep files focused, expose meaningful interfaces, and reuse systems across player/enemy where practical.
4. Record decisions and implementation/validation notes. Preserve existing networking authority and asset GUIDs when moving assets.
5. No automated tests without an explicit request. Validate through compilation, code review and manual Play Mode observations; restore editor state afterward.
6. Use Unity's official local MCP connection: Unity CLI (`unity mcp`) plus `com.unity.pipeline`. Discover the connected Editor's available commands and use its Unity APIs for asset and package changes. The former third-party MCP package and generated skills were removed on 2026-10-14. See [setup and validation](UnityMcpSetup.md).
